# 문의 하나로 Agent 전체 연결을 완성한다

<p class="lead">앞에서 만든 조회 도구·Agent·Graph·검토 기능을 연결합니다. 먼저 코드가 정한 순서로 문의를 처리하고, 이어서 모델이 MCP 도구와 A2A 검토자를 선택하도록 Agent를 완성합니다.</p>

마지막에는 **같은 정책 근거가 조회 → 초안 → 검토까지 이어졌는지**, 그리고 **다음 행동을 모델과 코드 중 누가 정했는지** 실행 기록으로 설명합니다.

## 통합 실습 A · 문의 하나를 끝까지 처리합니다

<p class="section-time">6분 · 17:35–17:41 · 노트북 6A → 6B → 6C</p>

`topic`을 `"계정"`, `contact`를 `"user@example.test"`로 설정합니다. 실행 전에 예상 정책 ID·담당 팀·방문 경로를 적고, 6A부터 순서대로 실행합니다.

|실행할 셀|연결되는 기능|출력에서 확인할 것|
|---|---|---|
|6A|MCP 서버에서 정책 조회|`snapshot`의 P-02·IT지원팀|
|6B|Graph 분기 → Agent 초안 → 검토·필요 시 수정|`result`의 `visited`, `draft`, `decision`, `history`와 `generation_records`|
|6C|A2A 검토 → 결과 수용|`review`의 Task 상태·산출물과 `decision`|

6B의 Agent는 6A에서 조회한 정책 사본을 도구로 읽습니다. `result["data"]`의 정책 ID·담당 팀이 `result["draft"]`에도 정확히 이어지는지 대조합니다. 초안이 처음부터 통과했다면 수정 호출이 없는 것이 정상입니다. 6A에서 수정 함수도 준비하므로 3번의 선택 심화를 실행하지 않았어도 진행할 수 있습니다.

<mark class="key-point">로컬 검토가 passed일 때만 원격 검토로 넘어갑니다. 원격 Task가 completed여도 요청 ID·초안 버전·검토 판정이 맞아야 accepted입니다.</mark>

이어서 `contact`를 빈 문자열로 바꾸고 6A → 6B → 6C를 다시 실행합니다. `lookup → ask`에서 멈추고 원격 검토를 건너뛰는지 확인합니다. 이때 `review`와 `decision`은 `None`이어야 합니다. 앞 요청의 `accepted`를 새 요청의 결과로 읽지 않습니다.

## 통합 실습 B · 모델이 도구와 검토자를 선택하게 만듭니다

<p class="section-time">14분 · 17:41–17:55 · 노트북 6D</p>

이번에는 업무 순서를 모두 코드로 고정하지 않습니다. **MCP 정책 조회, Card 발견, A2A 위임을 한 Agent에 연결하고 모델이 요청에 맞는 도구와 담당자를 선택하도록 만듭니다.**

### 1. Agent 연결을 작성합니다 · 6분

6D 정의 셀의 `build_connected_agent`를 완성합니다.

1. 인자로 받은 `mcp_tools`와 `discover_agents`·`delegate_to_agent`를 한 도구 목록으로 묶습니다.
2. `create_agent`에 모델과 도구 목록을 전달합니다.
3. 지침에 Card의 기능을 비교해 담당자를 고르는 기준과 위임 전에 확인할 조건을 작성합니다. 정책 근거가 없으면 담당 팀을 추측하지 않고 추가 정보를 요청하도록 합니다.

서버 시작·종료와 HTTP 요청은 실행 함수가 처리합니다. 각 도구의 역할을 읽고 어떤 선택을 모델에 맡기는지 판단합니다.

|도구|하는 일|남는 증거|
|---|---|---|
|MCP 조회 도구|업무의 정책 근거 조회|정책 ID·담당 팀 또는 `found=false`|
|`discover_agents`|후보 서버에서 Agent Card 조회|`discovery_records`의 이름·설명·기능·접속 방식|
|`delegate_to_agent`|선택한 Agent에 검토 요청|`review_records`의 선택 기능·Task ID·검토 결과|

후보 주소 두 개는 미리 주어집니다. 모델은 도구로 실제 Card를 읽고 기능을 비교합니다. Card가 업무 입력을 자동으로 만들어 주지는 않습니다. 검토 입력인 `topic`·`draft`·`request_id`·`version`은 두 서버와 합의한 형식입니다. 도구 인자 `skill_id`도 선택 근거를 확인하기 위한 값이며 A2A SendMessage의 표준 라우팅 필드는 아닙니다.

### 2. 두 요청을 실행하고 선택을 비교합니다 · 6분

정의 셀을 실행한 뒤 짧은 실행 셀의 `mission`을 다음 두 요청으로 바꿔 각각 실행합니다. 요청에 정답 후보 ID를 넣지 않습니다.

|요청|예상 선택|확인할 결과|
|---|---|---|
|계정 초안의 정책 근거를 검증해 주세요.|정책 조회 → Card 발견 → 정책 검토자|P-02·IT지원팀, `review-policy`, Task ID와 수용 판단|
|“그거 처리해 주세요”의 불명확한 표현만 검토해 주세요.|Card 발견 → 표현 검토자|`review-style`, 표현 검토 의견|

정책 검토자는 JSON-RPC, 표현 검토자는 A2A HTTP+JSON을 사용합니다. SDK는 Card의 `supportedInterfaces`에 따라 연결합니다. [ACP 통합과 REST 형태의 A2A](./a2a#acp-rest)에서 두 바인딩을 비교할 수 있습니다.

### 3. 답변과 기록을 대조합니다 · 2분

두 실행의 `discovery_records`와 `review_records`를 비교합니다. **“검토했습니다”라는 답변만으로 완료를 판단하지 않습니다.** 실제 Card를 읽었는지, 요청에 맞는 기능을 선택했는지, 해당 서버가 Task와 결과를 반환했는지 확인합니다. 표현 검토 완료는 정책 검토 통과를 뜻하지 않습니다.

선택이 예상과 다르면 Card 설명·요청·Agent 지침 중 모호한 부분을 찾아 수정합니다. 시간이 남으면 `reverse_candidates=True`로 후보 순서를 바꾸거나 “없는업무의 담당 팀을 알려 주세요”를 실행합니다. 미등록 업무라면 원격 검토 없이 추가 질문으로 끝나야 합니다.

## 풀이 · 두 실행에서 무엇이 달라졌나요?

<p class="section-time">풀이와 마무리 5분 · 17:55–18:00</p>

`build-agent-solution.ipynb`의 6A~6C 실행과 6D 정의 셀·“6D 풀이”를 엽니다. 함수 연결뿐 아니라 자신의 호출 기록이 아래 조건을 만족하는지 비교합니다.

|관찰한 결과|해석|예상과 다를 때 볼 곳|
|---|---|---|
|6A에서 P-02·IT지원팀 조회|MCP를 통해 근거를 확보했습니다.|조회 입력과 정책 응답|
|6B에서 `lookup → draft → review`|업무 분기가 초안 작성을 허용했습니다.|연락처·정책 존재 여부와 조건 함수|
|빈 연락처에서 `lookup → ask`, 원격 검토 없음|필수 정보가 없어 후속 작업을 멈췄습니다.|분기와 6C의 실행 조건|
|Task는 completed, 수용은 held|작업은 끝났지만 현재 초안의 통과 근거가 부족합니다.|요청 ID·버전·검토 판정|
|6D에서 두 요청이 다른 기능을 선택|모델이 Card 기능을 비교해 위임했습니다.|Card 조회 기록과 위임 도구의 인자|
|도구 목록만 있고 호출 기록 없음|등록했지만 아직 사용하지 않았습니다.|모델의 도구 요청과 실행 응답|

6A~6C에서는 코드가 원격 검토의 실행 조건을 정합니다. 6D에서는 모델이 발견·위임 도구를 선택합니다. 지침을 개선하면 선택을 유도할 수 있지만, **반드시 거쳐야 하는 검토는 코드의 실행 조건과 결과 검사로 보장해야 합니다.**

## 마무리 · 어떤 연결을 완성했나요?

실행한 요청 하나를 골라 다음 세 문장을 자신의 값으로 완성합니다.

- “MCP에서 조회한 ___을 근거로 Agent가 ___을 작성했다.”
- “A2A로 ___에게 검토를 맡겼고, Task ___의 결과를 ___ 때문에 수용하거나 보류했다.”
- “모델에는 ___ 선택을 맡겼지만, ___ 조건은 코드로 보장해야 한다.”

이제 도구·Agent·Graph를 만드는 데서 나아가 외부 조회와 독립 검토 시스템을 연결했습니다. DeepAgents에서 구성한 파일·Skill·위임 기능도 이런 작업을 수행하는 Agent의 실행 환경에 사용할 수 있습니다. 필요한 부품은 업무가 요구하는 도구와 제어 조건에 따라 고릅니다.

이번 결과는 **검토한 초안**입니다. `accepted`는 메일 발송을 뜻하지 않습니다. 실제 발송을 붙이려면 수신자·내용 확인, 발송 권한과 중복 발송 방지 조건을 추가해야 합니다.

### 업무 별칭을 추가합니다

<p class="section-time">선택 복습 · 15분</p>

앞 단계의 구현을 마친 뒤 새 요구를 받았습니다. **로그인 문의는 계정 정책으로, 비용 문의는 정산 정책으로 조회**되어야 합니다. 정책 두 건을 복제하거나 모델 프롬프트에 정답 팀을 추가하지 않습니다. 기존 함수 인자와 반환 구조는 유지합니다.

수정 위치와 구현 방법은 먼저 스스로 정합니다. 다음 계약만 지킵니다.

|입력|반환 topic|결과|
|---|---|---|
|로그인|계정|P-02|
|앞뒤 공백이 있는 비용|정산|P-01|
|정산·계정|기존과 같음|기존 정책 유지|
|로그인 장애·비용 취소|공백만 정리한 원문|미등록, found=false|

별칭은 명시된 두 단어만 지원합니다. 문장에 단어가 들어 있다는 이유로 정책을 추측하지 않습니다. 정책 dict 정본을 바꾸지 않으며, 호출 순서에 따라 결과가 달라져서도 안 됩니다.

**예측·실패 확인 3분 → 구현 7분 → 검사·실제 연결 5분**으로 진행합니다. 시작 전에 현재 구현이 실패할 행을 표시합니다. 아래 첫 검사에서 실패한 뒤 수정하고 다시 검사합니다. 실패 메시지를 숨기거나 기대값을 고쳐 통과시키지 않습니다.

<div class="command-purpose">내 구현 실행</div>

```python
# 노트북에 새 셀을 추가합니다.
for text in ["로그인", " 비용 ", "정산", "계정", "로그인 장애", "비용 취소"]:
    print(text, json.loads(lookup_policy(text)))
```

위 표와 비교한 뒤 6번 통합 셀의 topic을 로그인으로 바꿔 실행합니다.

새 계약과 기존 계약을 모두 검사합니다. 실제 연결에서는 `result.data.topic=계정`, P-02·IT지원팀, 최종 수용 판단을 확인합니다. 서버 응답의 topic을 별칭 그대로 두면 뒤의 Agent가 정규 업무명으로 다시 조회할 때 문제가 생길 수 있습니다. 어디서 이름을 정리하고 이후 단계에 무엇을 전달할지 설명합니다.

변경 전후의 검사 결과를 비교하고, 미등록 별칭 하나를 직접 골라 기존 동작이 유지되는지 확인합니다.


풀이: `build_lab/transfer_solution.py`에서 별칭을 정규 업무명으로 바꾸는 위치와 기존 입력을 유지하는 방법을 비교합니다.
