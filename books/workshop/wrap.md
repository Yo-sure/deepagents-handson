노트북의 **6. 통합** 셀에서 입력을 변경하고 Shift+Enter로 실행합니다.

학생 MCP 서버의 정책 조회→제공 Graph와 학생 분기→학생 LangChain Agent의 초안→제공 루프의 검토·필요 시 수정→A2A 검토→학생 수용 판단을 확인합니다. 초안이 처음부터 통과하면 수정하지 않습니다. 수정이 필요하면 정책·초안·피드백을 모델에 전달합니다.

로컬 검토가 passed인 경우에만 A2A 검토로 넘어갑니다. ask·held·stalled이면 원격 검토를 실행하지 않습니다. 원격 검토가 완료돼도 요청·버전·판정이 맞지 않으면 학생 수용 함수가 보류해야 합니다.

현재 예제는 정책 갱신 배포를 자동 동기화하지 않습니다. DeepAgents는 앞의 별도 예제에서 비교하며, 통합에 프레임워크를 중복으로 얹지 않습니다.

노트북의 ‘6. 통합’ 셀 아래에서 Graph 결과와 원격 검토, 수용 판단을 확인합니다. 정책은 snapshot, 그래프 상태는 result, 원격 검토는 review에 남습니다.

| 단계 | 찾을 증거 | 확인할 질문 |
|---|---|---|
|MCP 조회 결과|result.data|조회한 규정 ID와 담당 팀은 무엇인가?|
|LangGraph|result.visited, result.decision|초안 작성 경로를 택한 이유는 무엇인가?|
|LangChain|6B의 generation_records|도구 결과와 답변의 근거가 같은가?|
|수정 루프|result.history, result.draft, result.decision|수정을 했는가? 하지 않았다면 왜인가?|
|A2A 검토|review.state, review.artifact, decision|현재 요청의 완료 상태와 검토 통과를 함께 확인했는가?|

조회한 정책은 요청 단위의 snapshot으로 초안 생성에 전달됩니다. Agent의 도구 호출은 이 snapshot을 읽으며 호출할 때마다 MCP 서버를 다시 조회하지 않습니다. `result["data"]`와 최종 `result["draft"]`를 직접 대조합니다. HTTP 도구 목록과 응답 포장까지 다시 확인하려면 노트북 4A 셀의 출력를 읽습니다.

모델 호출이 실패하면 해당 단계의 오류를 해결한 뒤 다시 실행합니다. <mark class="key-point">실제 호출과 결과 전달이 확인되어야 통합 실습을 완료한 것입니다.</mark>

## 직접 연결: Agent가 조회하고 원격 검토를 요청합니다

<p class="section-time">예상 16분 · 17:39–17:55</p>

노트북의 **6D**를 실행합니다. 이번에는 미리 정한 검토 함수를 고르는 데서 더 나아가, **실제 Agent Card 두 개를 읽고 요청에 맞는 담당자를 선택**합니다. 후보 주소는 수업이 제공합니다. 인터넷 전체를 검색하는 예제는 아닙니다.

|누가 하는 일인가|실제 동작|출력에서 찾을 증거|
|---|---|---|
|제공 코드|MCP와 후보 A2A 서버 두 개 시작|후보 주소 목록|
|모델 → discover_agents 도구|각 서버의 Card를 HTTP로 조회|name·description·skills·supportedInterfaces|
|모델|Card의 기능을 비교해 담당자 선택|delegate_to_agent의 agent_id·skill_id|
|도구·SDK|선택한 서버에 A2A 요청 전송|JSON-RPC 또는 HTTP+JSON 바인딩, 실제 Task ID|
|모델|도구 결과를 읽고 선택 이유·결과 설명|최종 답변과 실제 검토 기록의 일치|

|Card를 읽어 발견하는 것|수업 코드가 미리 합의한 것|
|---|---|
|담당 기능·서버 주소·지원 바인딩|검토 입력 topic·draft·request_id·version과 ReviewResult 내용|

`skill_id`는 수업 도구가 Card의 선택 근거를 검사하는 인자이며, A2A SendMessage의 표준 라우팅 필드가 아닙니다. [공식 AgentSkill·메시지 정의](https://a2a-protocol.org/latest/specification/#445-agentskill) 실제 요청은 Message에 담아 보내고 서버의 업무 로직이 처리합니다. Card를 읽는 것만으로 서로 다른 업무 입력 형식까지 자동 변환되는 것은 아닙니다.

정책 검토자는 정책 ID·담당 팀을 검사하고, 표현 검토자는 문장의 불명확한 점을 검토합니다. 표현 검토가 끝나도 정책을 통과했다는 뜻은 아닙니다. 모델은 이름이나 나열 순서 대신 **Card에 공개된 기능**으로 선택해야 합니다.

**예측 3분 → 연결 코드 확인·정책 검토 실행 7분 → 표현 검토 실행·비교 6분**으로 진행합니다. 제공된 `run_connected_agent` 정의에서 `connected_tools`가 MCP 도구와 `discover_agents`·`delegate_to_agent`를 묶는 지점을 찾습니다. 이어지는 짧은 실행 셀에서 `mission`을 바꾸고 함수를 호출합니다. 정답 후보 ID를 요청에 넣지 않습니다. 정책 검토와 표현 검토의 두 실행을 필수로 비교하고, 미등록 문의는 시간이 남으면 실행하거나 수업 뒤 복습합니다.

|요청|예상 실행|확인할 결과|
|---|---|---|
|계정 초안의 정책 근거 검증|MCP 조회 → Card 발견 → 정책 검토자 선택|P-02·IT지원팀, review-policy, Task ID·accepted|
|“그거 처리해 주세요”의 불명확한 표현만 검토|Card 발견 → 표현 검토자 선택|review-style, HTTP+JSON, 표현 검토 의견|
|없는업무의 담당 팀 조회|MCP 조회 후 추가 질문|found=false, 원격 검토 기록 없음|

`discovery_records`에는 HTTP로 읽은 실제 Card, `review_records`에는 선택과 실행 결과가 남습니다. “검토했다”는 답변만 있고 기록이 없다면 미완료입니다. 선택이 예상과 다르면 Card 설명과 요청 중 모호한 부분을 찾아 수정하고 다시 실행합니다. 선택 실험으로 `await run_connected_agent(mission, reverse_candidates=True)`를 호출하면 후보의 제시 순서를 바꿀 수 있습니다. 순서가 바뀌어도 같은 기능을 선택하는지 확인합니다.

6A는 코드가 MCP를 조회하며 모델을 호출하지 않습니다. 6B는 Agent가 초안을 만들고 필요하면 수정 모델을 호출합니다. 6C는 코드가 원격 검토를 호출하고 서버 내부에서 모델이 표현을 검토합니다. 6D에서는 바깥 모델이 발견·위임 도구까지 선택하며, 선택한 서버의 검토 모델도 실행됩니다.

정책 검토 서버는 JSON-RPC, 표현 검토 서버는 **A2A HTTP+JSON/REST**를 제공합니다. SDK가 Card의 `supportedInterfaces`를 읽어 연결합니다. [ACP 통합과 REST 형태의 A2A](./a2a#acp-rest)에서 같은 작업을 두 바인딩으로 표현하는 방법을 비교합니다.

먼저 다음 네 칸을 한 줄씩 적습니다. 선택한 문제의 입력은 무엇인지, 어떤 데이터를 사용할 수 있는지, 무엇을 성공으로 볼지, 실패를 어떤 결과로 확인할지 적습니다. “정확하게 답한다”처럼 해석이 다른 표현은 관찰 가능한 조건으로 바꿉니다.

입력·환경·채점 기준을 정하는 방법을 더 읽으려면 다음 글을 참고합니다.

심화 반례: “P-01: 재무지원팀에는 절대 문의하지 마세요.”는 이름·ID 검사를 통과합니다. 로컬 `inspect_draft`와 원격 `verify`는 별도 함수이지만 모두 이름·ID를 중심으로 검사하므로 두 번 검사해도 같은 맹점이 남습니다. 두 검사 모두 팀명과 ID만 찾는다면 잘못된 문장을 두 번 통과시킬 수 있습니다. 두 번째 검사에서 무엇을 다르게 확인해야 할까요?

## 풀이와 다음 학습

<p class="section-time">예상 5분 · 17:55–18:00 · 두 실행 비교와 마무리</p>



6D에서는 모델의 도구 선택 기록이 실행 증거입니다. 필요한 Card 발견이나 A2A 검토가 누락되었다면 지시를 명확히 해 재실행할 수 있지만, 이것이 검토 실행의 보장은 아닙니다. 업무상 필수라면 6C처럼 코드가 검토를 호출하고 수용 조건을 검사합니다.

MCP는 외부 조회 기능을 연결하고, A2A는 별도 검토 시스템의 작업과 결과를 연결합니다. 하나의 Agent가 두 연결을 도구로 사용하는 모습을 실제로 확인했습니다. 앞의 Graph 방식은 순서와 분기를 제어하기 쉽고, 6D는 모델이 요청에 맞춰 도구를 선택할 수 있습니다. 어느 방식이 나은지는 반드시 지켜야 하는 업무 조건에 따라 정합니다.

별칭 변경을 복습했다면 `build_lab/transfer_solution.py`와 비교합니다. 입력을 정규 업무명으로 변환한 뒤 기존 정책을 조회하며, 기존·새 별칭·미등록 입력을 함께 검사합니다.

### 업무에 가져갈 때 마지막으로 고를 것

5분 동안 6C와 6D의 기록을 나란히 보며 검토를 누가 선택했는지, 무엇이 코드로 보장되는지 설명합니다. 다음 네 질문 중 하나를 골라 업무 적용점을 덧붙입니다.

1. 지금 방식이 실패하는 구체적인 입력은 무엇인가요?
2. 새 구성을 쓰면 어떤 점이 나아지나요?
3. 대신 늘어나는 호출·대기·운영 부담은 무엇인가요?
4. 같은 입력으로 두 방식을 비교해 무엇을 확인하겠습니까?

단순한 구성으로 요구를 만족하면 거기서 멈춰도 됩니다. 오늘 배운 부품을 모두 넣는 것이 목표는 아닙니다.
