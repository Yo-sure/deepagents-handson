# Loop·Graph 설계 — 다음 작업과 검증을 연결하기

코딩 Agent가 “수정했습니다”라고 답했습니다. 이제 무엇을 실행하고, 어떤 결과를 확인해야 이 작업을 끝낼 수 있을까요? 사람이 매번 다음 지시를 입력하던 과정을 실행 규칙으로 옮겨 봅니다.

이 자료는 **실패 한 건을 수정 담당에게 전달하고, 두 검토 결과를 모아 다음 행동을 정하는 사례**를 따라갑니다. 읽은 뒤에는 담당자별 입력·산출물, 병렬 실행할 단계, 재검토와 중단 조건을 한 장의 설계 메모로 설명할 수 있어야 합니다.

Harness 수업에서 이 활동을 마쳤다면 필요한 부분만 다시 읽습니다. 실습은 같은 `harness-control.ipynb`와 `build-agent.ipynb`의 ‘Harness 설계 메모’를 사용합니다. 별도 프로젝트를 만들 필요는 없습니다.

## “수정 완료” 뒤에 남는 네 가지 결정

문의 Agent가 공백 연락처에도 초안을 만드는 오류를 발견했다고 가정합니다. 앞에서 만든 **문의 Agent가 수정 대상**이고, 파일을 고치는 **코딩 Agent가 구현 담당**입니다. 둘의 역할을 구분한 뒤 다음 결정을 내립니다.

|설계할 결정|이 사례에서 정할 내용|관점|
|---|---|---|
|무엇을 보고 수정하는가?|실패 입력, 기대 경로, 현재 코드와 검사 결과 전달|Context|
|무엇을 실행할 수 있는가?|코드 편집·검사 도구 제공, 요구사항 변경 권한 제한|Harness|
|언제 다시 실행하고 멈추는가?|실패하면 수정, 같은 후보 반복이나 수정 예산 소진이면 인계|Loop|
|어떤 결과를 기다리는가?|기능 검토와 설명 검토를 모아 같은 후보의 결과인지 확인|Graph|

이 표의 Loop·Graph는 설계 문제를 구분하기 위한 표현입니다. 표준화된 발전 단계나 특정 제품의 기능 이름으로 외우지 않습니다. 한 실행 안에서도 네 가지 결정이 함께 필요합니다.

### 다음 실행에 무엇을 남길까요? {#context-selection}

“공백 입력을 고쳐 주세요”만 전달하면 담당자는 기대 동작부터 추측해야 합니다. 다음처럼 **입력과 기대 결과를 재현할 수 있는 형태**로 전달합니다. 아래는 실행 코드가 아닌 작업 전달 기록의 예입니다.

```text
후보: v1
실패: F1 — 연락처가 공백인데 초안을 생성함
입력: topic="계정", contact="   "
기대: lookup → ask / 초안 생성 호출 0회
실제: lookup → draft → review / 초안 생성 호출 1회
수정 대상: route_inquiry와 해당 검사의 코드
변경 금지: 공백 연락처에는 추가 정보를 요청한다는 요구사항
완료 근거: 새 후보에서 같은 입력과 정상 입력을 다시 검사한 결과
```

기록에는 현재 코드의 위치도 함께 남깁니다. 담당자가 위치를 모르면 먼저 관련 함수와 검사를 찾게 합니다. 전체 저장소나 과거 로그를 처음부터 모두 붙이기보다, 원인을 판단하는 데 필요한 자료부터 읽고 부족한 부분을 추가로 조회합니다. Anthropic의 Context Engineering 글은 필요한 정보의 선택, 도구를 통한 조회, 긴 실행의 요약과 외부 메모를 다룹니다. [원문과 사례](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

|지금 전달|필요할 때 조회|요약해도 남겨야 할 것|
|---|---|---|
|현재 후보, 재현 입력, 기대·실제 결과, 관련 코드|전체 실행 로그, 다른 파일, 과거 수정 이력|요구사항의 예외, 미해결 문제, 이미 실패한 수정과 근거 위치|

<mark class="key-point">기록을 저장하는 것과 다음 모델이 그 기록을 읽는 것은 별개입니다.</mark> 다음 입력에 포함하거나 조회 도구로 읽도록 연결해야 합니다. 특히 이전 후보의 통과 기록을 현재 후보의 결과로 섞지 않습니다.

**판단해 보기:** 위 기록에서 ‘실제 경로’와 ‘기대 경로’를 지우면 무엇을 판단하기 어려울까요? 정답 코드를 주는 것과 성공 조건을 주는 것은 어떻게 다를까요?

<details><summary>길잡이 · 수정 방법과 성공 조건을 구분합니다</summary>

실제 경로가 없으면 오류가 어느 단계에서 드러났는지, 기대 경로가 없으면 무엇으로 고쳐야 하는지 불분명합니다. 성공 조건은 만족해야 할 동작을 고정합니다. 구현 담당은 그 조건 안에서 수정 방법을 선택할 수 있습니다.

</details>

## 실패 보고를 다음 작업으로 바꿉니다

사람이 “검사해”, “실패했으니 다시 고쳐”, “이제 끝내”를 매번 입력하는 대신 다음 규칙을 정합니다. 아래는 코딩 Agent를 운영하는 **설계 예시**이며, 현재 노트북이 이 자동화 전체를 구현한 것은 아닙니다.

|시점|시스템이 할 일|남길 근거|
|---|---|---|
|실패 도착|현재 후보의 미해결 문제인지 확인하고 담당자 배정|후보 버전, 실패 ID, 재현 입력|
|수정 완료 보고|원래 요구에 대한 검사를 다시 실행|변경 범위, 실행한 검사, 실제 결과|
|검사 실패|남은 수정 예산과 이전 시도를 보고 재수정 또는 인계|실패 이유, 직전 후보와 달라진 점|
|검토 완료|필수 결과가 모두 같은 후보를 가리키는지 확인|검토별 후보 버전과 판정|
|종료|통과 근거와 함께 최종 확인을 요청하거나 미해결 내용을 인계|완료 이유 또는 중단 이유|

<mark class="key-point">수정 담당의 완료 선언은 검사를 시작할 신호입니다. 검사 통과를 대신하지 않습니다.</mark> 요구사항을 `ask`에서 `draft`로 바꿔 얻은 PASS도 원래 문제를 해결한 증거가 아닙니다.

노트북의 `refine_answer`에서는 한 초안에 대한 검토·수정·중단을 관찰했습니다. 여기에 새 작업 발견, 담당자 배정, 실행 간 기록을 더하면 여러 요청에 걸친 운영 설계로 확장됩니다. 이때 동일 실패 ID라도 후보와 재현 입력이 달라졌다면 새 결함인지 다시 판단해야 합니다.

## 두 검토를 병렬로 맡기고 결과를 기다립니다

수정된 후보 v2를 기능 검토와 교재 설명 검토에 전달합니다. 기능 검토는 공백·정상 입력의 경로를 실행하고, 설명 검토는 셀의 출력 필드와 안내 문장을 대조합니다. 두 검토는 서로의 결과 없이 시작할 수 있지만, 최종 판단에는 둘 다 필요합니다.

![같은 후보를 기능·교재 검토에 나누어 보내고, 두 결과를 기다린 뒤 수정 또는 최종 확인으로 진행하는 흐름](/images/graph-review-join.svg)

|역할|입력|산출물|수정 권한|
|---|---|---|---|
|구현 담당|실패 기록과 현재 코드|새 후보와 변경 내역|합의된 코드·설명 범위|
|기능 검토|새 후보와 원래 요구|입력별 실제 경로·호출 수·통과 여부|검토 중 후보는 변경하지 않음|
|설명 검토|같은 후보의 셀과 안내|일치 여부와 어긋난 위치|검토 중 후보는 변경하지 않음|
|취합 담당|두 검토 결과|재수정·보류·최종 확인 중 다음 행동|누락된 검토를 임의로 통과 처리하지 않음|

검토 중 코드를 바꾸면 서로 다른 후보의 결과를 합칠 수 있습니다. 검토할 후보를 고정하고, 수정이 생기면 새 후보에 필요한 검토를 다시 요청합니다. **기능 검토 v2 통과 + 설명 검토 v1 통과는 v2의 전체 통과가 아닙니다.**

### 그래프의 한 노드 안에는 무엇이 들어갈까요?

앞 LangGraph 실습에서는 노드 함수가 상태를 읽고 갱신을 반환했습니다. 같은 바깥 구조에서 노드가 Agent를 호출하거나 컴파일된 하위 그래프를 실행하도록 구성할 수도 있습니다. 공유하는 상태 키가 있으면 하위 그래프를 노드로 넣고, 입력·출력 형식이 다르면 바깥 함수에서 변환합니다. [LangGraph 공식 하위 그래프 예제](https://docs.langchain.com/oss/python/langgraph/use-subgraphs)

|바깥 그래프가 보는 단계|안에서 실행할 수 있는 것|바깥으로 돌려줄 결과|
|---|---|---|
|기능 검토|검사 함수 또는 검사 도구를 사용하는 Agent|후보 버전, 검사 근거, 판정|
|설명 검토|모델 호출 또는 읽기 도구를 사용하는 Agent|후보 버전, 불일치 위치, 판정|
|수정|편집·실행 도구와 지침을 갖춘 코딩 Agent|새 후보와 변경 내역|

안쪽 Agent가 여러 번 도구를 호출하더라도 바깥 그래프는 약속된 결과를 받아 다음 단계를 정합니다. 모든 노드를 Agent로 만들 필요는 없습니다. 요구가 명확한 검사와 취합은 일반 함수로 두면 실행과 해석이 단순해집니다.

### 병렬로 나누기 전에 확인합니다

Agent A가 함수 이름을 바꾸고 B가 그 함수를 호출하는 코드를 바꾼다면 두 작업에는 의존성이 있습니다. 새 이름과 입력·출력 계약을 먼저 합의하거나, A의 변경을 받은 뒤 B가 작업하도록 순서를 정합니다. 단순히 담당자가 둘이라는 이유로 병렬화하지 않습니다.

**설계 질문:** 기능 검토에 4분, 설명 검토에 6분, 취합에 2분이 걸린다면 병렬화로 얼마나 줄어들까요? 검토 중 후보가 바뀌면 이 계산은 여전히 유효할까요? 풀이에서 대기 시간과 비용을 따로 비교합니다.

## 개인 활동: 다음 지시를 누가 만드는가

<p class="section-time">예상 20분 · 해당 수업 시간에 포함</p>

`build-agent.ipynb`의 **‘Harness 설계 메모’** Markdown 셀에 작성합니다. 셀을 두 번 눌러 편집하고 Shift+Enter로 저장한 내용을 표시합니다. 코딩 Agent에게 검수 작업을 맡길 때 필요한 실행 순서를 설계합니다. 모델 호출이나 별도 파일 작성은 필요하지 않습니다.

### 상황: 코드와 설명이 서로 다른 결과를 말합니다

오전에 만든 문의 Agent의 새 버전 v1을 검수한다고 가정합니다. 기능 검토와 설명 검토가 다음 두 문제를 발견했습니다. 아래 내용은 **연습용 가상 기록**입니다. 자신의 정상 코드를 일부러 망가뜨리지 않습니다.

|발견한 문제|재현 근거|원래 요구|
|---|---|---|
|공백 회신 대상으로 초안을 생성함 — 기능 검토 F1|계정 문의, contact="   " → 방문 lookup→draft→review, 초안 생성 호출 1회|공백이면 lookup→ask, 초안 생성 호출 0회|
|노트북 출력 설명이 실제 필드와 다름 — 설명 검토 D1|실행 셀은 result["decision"]을 출력하는데 안내 문장은 result["status"]를 읽으라고 함|학습자가 출력에서 분기 판정을 찾을 수 있도록 실제 필드와 설명이 일치해야 함|

F1과 D1은 이 두 문제를 구분하는 번호입니다. 수정한 버전은 v2로 부릅니다. 기능 검토자는 공백 입력을 다시 실행하고, 설명 검토자는 v2의 셀과 안내 문장을 대조합니다.

### 먼저 실행으로 경계를 확인합니다 · 5분

workshop 폴더의 `notebooks/harness-control.ipynb`를 열고 위에서부터 실행합니다. `candidate_drafts`에 자신이 만든 수정 후보 두 개를 넣어, **첫 수정은 실패하지만 마지막 허용 수정에서 통과**하게 만듭니다. 처음부터 정답만 반환하지 않습니다. 실행 전에 수정 호출 수·검토 횟수·종료 상태를 예측하고 출력과 대조합니다.

이어서 같은 초안을 반복해서 반환하도록 바꿉니다. 실패 이유가 계속 같다는 것과 초안 자체가 전혀 바뀌지 않는 것을 구분합니다. 여기서는 모델을 호출하지 않고 수정 결과를 통제해 바깥 제어 규칙을 확인합니다. 실제 모델의 답변 품질은 앞의 모델 실행 결과에서 따로 확인합니다.

### 이어서 만들 설계 메모 · 15분

1. **실행 순서 하나 · 6분:** 문제 발견부터 수정, 두 검토, 결과 취합, 종료까지 화살표로 연결합니다. 각 단계 옆에 누가 무엇을 확인하는지 한 줄씩 적습니다. 동시에 할 수 있는 단계와 앞 결과가 필요한 단계를 구분합니다.
2. **반례 대응 세 개 · 6분:** 아래 상황마다 ‘다음 행동’과 ‘확인할 근거’를 한 줄씩 적습니다.
3. **자기 확인 · 3분:** 두 검토가 같은 v2를 확인했는지, 누락된 검토를 통과로 처리하지 않았는지 살펴봅니다. 수정 시도는 최대 2회라고 가정하고 해결되지 않았을 때 누구에게 무엇을 넘길지 적습니다.

|반례|자신의 설계에서 결정할 것|
|---|---|
|이미 해결한 F1 알림이 다시 도착함|새 수정 작업을 시작할지, 무엇을 확인한 뒤 결정할지|
|구현 담당이 기대값을 draft로 바꾼 뒤 PASS라고 보고함|완료로 받아들일지, 어떤 요구와 다시 대조할지|
|기능 검토만 끝났고 설명 검토 결과가 없음|기다릴지, 완료할지, 누구의 상태를 확인할지|

**완료 기준:** 반복 실험의 예측과 실제 호출·검토 횟수가 일치하고 그 이유를 설명합니다. 실행 순서에 수정·검증·종료가 있고, 세 반례마다 근거를 확인한 뒤 다음 행동을 결정합니다. 풀이의 문장과 같을 필요는 없습니다. ‘다시 해보라’만 반복하지 않고, 시도 상한에 도달하면 재현 입력과 마지막 검토 결과를 인계할 수 있어야 합니다.

<details><summary>먼저 마쳤다면 · 역할별 입력과 권한까지 정하기</summary>

구현·기능 검토·설명 검토·취합의 입력, 산출물, 수정 가능한 범위를 표로 적습니다. 두 역할이 같은 파일을 동시에 바꾸려 할 때 충돌을 어떻게 줄일지도 정합니다. 필수 결과를 완성한 뒤 진행하는 확장입니다.

</details>

코딩 도구를 사용할 수 있다면 자신의 메모를 보내 “세 반례에서 빠진 조건을 찾아 달라”고 요청하고 제안을 검토합니다. 계정이 없어도 같은 사례와 풀이로 활동을 마칠 수 있습니다.

## 풀이: 반복과 연결의 설계를 따로 확인합니다

<p class="section-time">예상 8분 · 해당 수업 시간에 포함</p>



F1과 D1은 처음에 병렬로 검토할 수 있습니다. 두 검토가 변경 전후 서로 다른 후보를 읽었다면 한 번의 합격 결과로 합치지 않습니다. 구현이 바뀐 뒤에는 새 후보를 기준으로 필요한 검토를 다시 합니다.

동일 후보·동일 입력에 대해 이미 해결한 F1 알림이 다시 온 경우에는 해결 근거를 확인하고 중복 수정 작업을 만들지 않습니다. 후보나 입력이 달라졌다면 다시 재현하여 새 문제인지 판단합니다. 검사를 바꿔 얻은 PASS는 원래 요구 충족의 증거가 아닙니다. 필수 검토가 빠졌다면 완료로 표시하지 않으며, 시도 상한을 넘기면 실패 입력과 마지막 근거를 사람에게 전달합니다.

|확인할 것|설명할 수 있어야 하는 이유|
|---|---|
|다음 일을 고르는 규칙|매번 사람의 후속 프롬프트가 필요하다면 자동 반복의 설계가 빠져 있음|
|실제 데이터 의존성|독립 검토를 직렬로 기다리거나 필요한 검토를 건너뛰지 않기 위해|
|후보 버전과 근거|서로 다른 코드에 대한 검사 결과를 합격으로 묶지 않기 위해|
|실행 간 상태|종료·중단 뒤 같은 실패를 처음부터 다시 배정하지 않기 위해|
|권한·중단 조건|구현 담당의 자신감만으로 작업 범위나 실행 시간을 늘리지 않기 위해|

검토 역할을 둘로 나누는 것만으로 정확성이 보장되지는 않습니다. 같은 잘못된 기준을 사용하면 같은 오류를 놓칩니다. 에이전트 수보다 검토 입력과 근거가 먼저입니다.

### 병렬 실행은 대기 시간과 총비용을 다르게 바꿉니다

다음 숫자는 계산을 위한 **가정**입니다. 실제 제품의 성능이나 요금 측정값이 아닙니다. 기능 검토 4분, 교재 검토 6분, 취합 2분이고, 두 검토가 같은 후보를 독립적으로 읽을 수 있다고 가정합니다.

|설계|대기 시간 계산|추가로 확인할 것|
|---|---|---|
|순차 검토|4 + 6 + 2 = 12분|단순한 실행과 기록 관리|
|병렬 검토 후 취합|max(4, 6) + 2 = 8분|같은 후보를 읽었는지, 두 결과가 모두 도착했는지|
|검토 중 후보 변경|이 계산으로 완료 시간을 확정할 수 없음|새 후보에 필요한 검토를 다시 해야 함|

병렬 실행도 두 검토의 모델 호출을 모두 사용합니다. 기다리는 시간이 줄어도 총 토큰 사용량이 같은 비율로 줄지는 않습니다. 역할마다 긴 문맥을 중복 전달하거나 취합에 추가 모델을 쓰면 비용이 늘 수 있습니다.

선택 확장에서 추가 비용을 적는다면 에이전트 수만 적지 않습니다. **불필요한 재실행, 중복 문맥, 취합, 사람의 최종 확인** 중 이 사례에서 가장 큰 비용 하나를 고르고 줄일 방법을 적습니다.

### 다음 실행을 허용할 근거를 남깁니다

|마지막 결과|다음 행동의 예|남길 기록|
|---|---|---|
|새 결함과 재현 입력이 확보됨|정해진 범위의 수정 한 번 배정|후보 버전, 실패 입력, 기대 결과|
|같은 결함에 같은 수정만 반복|자동 재배정을 멈추고 인계|이미 시도한 변경과 실패 근거|
|필수 검토 하나가 시간 안에 오지 않음|합격 취합을 보류하고 담당 실행 상태 확인|누락된 역할, 마지막 응답, 사용한 예산|
|원래 검사 통과, 필요한 검토 모두 확보|사람의 최종 확인으로 넘김|동일 후보에 대한 결과와 남은 한계|

시도 횟수·경과 시간·비용은 서로 다른 제한입니다. 횟수만 제한하면 한 실행이 오래 걸리는 문제를 막지 못합니다. 반대로 제한에 닿았다고 작업이 성공한 것은 아닙니다. 이 활동의 목적은 ‘끝날 때까지 반복’이라는 지시를 검증 가능한 실행·중단 조건으로 바꾸는 데 있습니다.

상태를 파일에 기록하는 것만으로 중복 배정이 사라지지는 않습니다. 두 실행이 동시에 같은 미완료 항목을 읽을 수 있기 때문입니다. 운영으로 옮길 때는 한 작업의 담당자를 어떻게 정하고, 담당 실행이 끊겼을 때 언제 다시 맡길지도 결정해야 합니다. 공통 활동에서는 그 규칙을 문장으로 쓰며 별도 스케줄러를 구현하지 않습니다.
