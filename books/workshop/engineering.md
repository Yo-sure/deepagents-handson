# 요즘 말하는 Loop Engineering과 Graph Engineering

“에이전트에게 다음 일을 시키는 사람”에서 “다음 일을 정하고 맡기는 시스템을 설계하는 사람”으로 역할이 옮겨간다는 주장이 퍼지고 있습니다. 여러 에이전트를 조직하는 Graph Engineering도 그 흐름에서 등장합니다.

이 절에서는 실제 발언과 글을 먼저 읽습니다. 이어서 무엇을 자동화하고 어떤 결과에서 멈출지, 여러 작업을 어떻게 연결할지 판단합니다. 특정 프레임워크의 API를 외우거나 자체 하네스를 구현하는 수업은 아닙니다.

공통 범위는 개념·사례·설계 활동입니다. 제품 계정 없이도 참여할 수 있습니다. LangGraph의 상태·분기 구현은 [별도 모듈](./graph)에서 배우며, 여기서 다루는 업계 용어와 동일시하지 않습니다.

### 용어의 차이를 읽습니다

|용어|이 자료들이 주로 묻는 질문|수업에서 구분할 예|
|---|---|---|
|Context Engineering|판단에 필요한 정보를 무엇으로 구성하고 남길 것인가?|관련 코드·요구·실패 기록을 다음 실행에 전달|
|Harness Engineering|에이전트가 일할 도구·환경·실행 제어를 어떻게 구성할 것인가?|파일 접근, Skill, 검증 명령, 권한과 실행 기록|
|Loop Engineering|사람이 매번 지시하지 않아도 무엇이 다음 실행을 시작하고 끝내게 할 것인가?|새 실패 발견→작업 배정→검증→상태 기록→재실행 또는 중단|
|Graph Engineering|여러 실행 주체의 일·정보·검증 권한을 어떻게 연결할 것인가?|독립 조사를 병렬로 맡기고 산출물을 모아 별도 검토|

이는 확인한 담론의 공통점을 정리한 표입니다. 저자마다 경계는 다릅니다. Addy는 하네스 위에서 반복 실행을 조직하는 데 무게를 두고, Hanako는 한 작업의 피드백 반복을 Loop, 전체 작업의 조정을 Graph로 설명합니다. 하나의 공식적인 발전 단계처럼 외우지 않습니다.

Context는 다른 구성에서도 계속 필요합니다. Anthropic의 설명처럼 무엇을 컨텍스트에 넣을지 판단하는 일은 에이전트가 반복하거나 여러 역할로 나뉘어도 사라지지 않습니다. [Context Engineering 원문](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

## 무엇이 달라지는가: 코드 검수 작업

다음은 원문의 관점을 교재에 적용한 **수업용 설계 예시**입니다. 실제 제품의 실행 로그나 내장 기능을 재현한 것이 아닙니다.

사람이 “공백 연락처를 확인해”, “실패했으니 수정해”, “다음 문제를 찾아”라고 매번 입력하면 다음 일을 선택하는 주체는 사람입니다. 이 과정을 시스템에 맡기려면 아래 조건이 필요합니다.

|결정|설계 예시|
|---|---|
|시작 계기|새 변경에 대한 검사 실패가 보고됨|
|작업 선택|아직 해결되지 않은 실패 한 건을 선택하고 중복 처리 여부 확인|
|실행|구현 담당에게 입력·기대 결과·변경 범위 전달|
|검증|구현 담당의 완료 선언과 별개로 원래 검사와 반례 확인|
|상태 저장|실패 ID, 변경 파일, 검사 근거, 남은 시도, 다음 행동 기록|
|중단|통과하면 해당 작업 종료. 같은 실패 반복 또는 예산 소진이면 사람에게 인계|

이것이 한 요청의 초안을 두 번 고치는 반복문보다 넓은 설계입니다. 현재 `refine_answer`는 피드백·중단 조건을 관찰하는 작은 실행 예제입니다. 주기적인 작업 발견이나 여러 실행에 걸친 진행 관리를 구현하지 않았으므로, 이를 Loop Engineering 전체 구현으로 소개하지 않습니다.

Addy는 자동화, 격리된 작업 공간, Skills, 연결 도구, 하위 에이전트와 외부 상태 저장을 조합하는 사례를 제시합니다. 이 수업은 구성 요소의 역할을 읽습니다. 제품별 명령과 자동화 기능은 설치된 버전에서 별도 확인하며, 이 절에서 백그라운드 작업을 실제로 등록하지는 않습니다. [원문 사례](https://addyosmani.com/blog/loop-engineering/)

## Graph Engineering은 누구의 일이 누구를 기다리는지 묻습니다

업무 문의 Agent의 새 버전을 검수한다고 가정합니다. 기능 검사와 교재 설명 검토는 같은 후보를 읽지만 서로의 결과가 없어도 시작할 수 있습니다. 최종 담당자는 두 결과가 있어야 다음 행동을 결정할 수 있습니다.

```text
같은 후보 버전
 ├─ 기능 검토 담당 ── 검사 결과 ─┐
 └─ 교재 검토 담당 ── 설명 결함 ─┴─ 결과 취합
                                     ├─ 결함 있음 → 구현 담당 → 새 후보 → 재검토
                                     └─ 통과 → 사람의 최종 확인
```

순서는 의존성이 아닙니다. “문서에 아래에 적혀 있어서 기다리는 일”과 “앞 작업의 결과를 읽어야 시작할 수 있는 일”을 구분합니다. 노드에는 역할·입력·산출물·실패 결과를, 연결에는 다음 단계로 갈 조건을 정합니다. 이는 Hanako가 강조한 의존성과 계약의 관점을 적용한 예입니다. [X 원문](https://x.com/hanakoxbt/status/2087167924410658912)

LangGraph는 이런 제어 흐름을 코드로 표현할 때 사용할 수 있습니다. 그러나 Graph Engineering이 곧 LangGraph 사용법이라는 뜻은 아닙니다. Codex의 하위 에이전트로 그래프 계약을 실행하려는 [커뮤니티 프로젝트](https://github.com/luxiaolei/graph-engineering)도 있습니다. 이는 활용 방식의 한 사례이며 해당 Skill을 수업 필수 설치로 요구하지 않습니다.

### 세 가지를 연결해 설명합니다

실패를 재현할 입력·관련 코드·검사 근거를 다음 실행에 전달하는 것은 Context 관점입니다. 실패를 확인해 다음 작업을 맡기는 반복은 Loop 관점입니다. 기능·교재 검토를 나누고 결과를 합치는 구조는 Graph 관점입니다. 이 구조 안에서도 각 역할은 도구와 실행 환경이 필요합니다.

## 개인 활동 · 20분: 다음 지시를 누가 만드는가

`workshop/build_lab/HARNESS_WORKSHEET.md`를 작성합니다. 기존 분기 코드를 다시 고치는 활동이 아니라, 그 코드를 검수하는 작업의 시작·배정·검증·다음 행동을 설계합니다.

### 제공하는 재료

기능 검토와 교재 검토는 같은 후보 v1을 읽습니다. 아래 기록은 판단 연습용 가상 입력입니다.

|기록|입력과 결과|
|---|---|
|기능 검토 F1|정책 있음·공백 연락처에서 draft 방문. 기대는 ask이며 초안 모델 호출은 없어야 함|
|교재 검토 D1|명령 예시는 학생 runner를 쓰지만 결과 설명은 옛 integration.json 필드를 참조|
|수정 후 v2|F1의 원래 검사 통과, D1의 명령·필드 대조 통과|
|추가 경계|이미 해결된 F1 알림이 다시 도착하거나, 구현 담당이 검사 기대값을 바꿔 PASS를 보고함|

실제 자신의 코드가 이미 올바르면 결함이 있다고 가정해 수정하지 않습니다. 가상 기록을 분석했다고 표시하거나, 자신의 실제 실행 기록으로 교체합니다.

### 작성 순서

1. **4분 — Loop:** 어떤 이벤트로 시작하고 어떤 실패를 다음 작업으로 선택할지 정합니다. 완료·정체·예산 소진의 결과를 각각 적습니다.
2. **6분 — Graph:** 구현·기능 검토·교재 검토·취합의 역할을 배치합니다. 병렬 가능한 작업과 반드시 기다려야 하는 연결을 표시합니다.
3. **6분 — 계약:** 각 역할의 입력, 산출물, 접근 범위를 적습니다. 실패 ID·후보 버전·검사 근거·시도 횟수를 어디에 남길지 정합니다.
4. **4분 — 반례:** 중복 F1, 검사 기대값 변경, 검토 하나가 누락된 경우의 다음 행동을 결정합니다.

계정이 있으면 아래 명세를 자신의 Codex·Claude Code 환경에 전달해 설계를 검토받을 수 있습니다. 실제 실행을 했는지와 설계만 검토했는지는 구분합니다. 계정이 없어도 동일한 입력으로 활동지를 작성하고 다음 풀이와 비교합니다.

```text
제공된 F1/D1 기록으로 코드 검수 작업을 설계하십시오.
작업을 시작할 조건, 다음 실패를 선택할 규칙, 종료와 인계 조건을 작성하십시오.
구현·기능 검토·교재 검토·결과 취합의 의존성과 산출물 계약을 명시하십시오.
독립된 검토는 병렬로 할 수 있지만 같은 후보 버전을 읽어야 합니다.
검사 기대값을 바꾼 PASS, 중복 알림, 검토 누락을 어떻게 처리할지 설명하십시오.
우선 설계만 검토하십시오. 실제 코드 변경이나 예약 실행을 했다고 보고하지 마십시오.
```

## 풀이: 반복과 연결의 설계를 따로 확인합니다

F1과 D1은 처음에 병렬로 검토할 수 있습니다. 두 검토가 변경 전후 서로 다른 후보를 읽었다면 한 번의 합격 결과로 합치지 않습니다. 구현이 바뀐 뒤에는 새 후보를 기준으로 필요한 검토를 다시 합니다.

중복 F1은 저장된 실패 ID와 해결 상태를 확인해 새 수정 작업으로 배정하지 않습니다. 검사를 바꿔 얻은 PASS는 원래 요구 충족의 증거가 아닙니다. 필수 검토가 빠졌다면 완료로 표시하지 않으며, 시도 상한을 넘기면 실패 입력과 마지막 근거를 사람에게 전달합니다.

|확인할 것|설명할 수 있어야 하는 이유|
|---|---|
|다음 일을 고르는 규칙|매번 사람의 후속 프롬프트가 필요하다면 자동 반복의 설계가 빠져 있음|
|실제 데이터 의존성|독립 검토를 직렬로 기다리거나 필요한 검토를 건너뛰지 않기 위해|
|후보 버전과 근거|서로 다른 코드에 대한 검사 결과를 합격으로 묶지 않기 위해|
|실행 간 상태|종료·중단 뒤 같은 실패를 처음부터 다시 배정하지 않기 위해|
|권한·중단 조건|구현 담당의 자신감만으로 작업 범위나 실행 시간을 늘리지 않기 위해|

검토 역할을 둘로 나누는 것만으로 정확성이 보장되지는 않습니다. 같은 잘못된 기준을 사용하면 같은 오류를 놓칩니다. 에이전트 수보다 검토 입력과 근거가 먼저입니다.

### 병렬 실행은 대기 시간과 총비용을 다르게 바꿉니다

다음 숫자는 계산을 위한 **가정**입니다. 실제 제품의 성능이나 요금 측정값이 아닙니다. 기능 검토 4분, 교재 검토 6분, 취합 2분이고, 두 검토가 같은 후보를 독립적으로 읽을 수 있다고 가정합니다.

|설계|대기 시간 계산|추가로 확인할 것|
|---|---|---|
|순차 검토|4 + 6 + 2 = 12분|단순한 실행과 기록 관리|
|병렬 검토 후 취합|max(4, 6) + 2 = 8분|같은 후보를 읽었는지, 두 결과가 모두 도착했는지|
|검토 중 후보 변경|이 계산으로 완료 시간을 확정할 수 없음|새 후보에 필요한 검토를 다시 해야 함|

병렬 실행도 두 검토의 모델 호출을 모두 사용합니다. 기다리는 시간이 줄어도 총 토큰 사용량이 같은 비율로 줄지는 않습니다. 역할마다 긴 문맥을 중복 전달하거나 취합에 추가 모델을 쓰면 비용이 늘 수 있습니다. Addy도 하위 에이전트의 비용과 사람이 검토할 수 있는 양을 함께 지적합니다. [원문 논의](https://addyosmani.com/blog/loop-engineering/)

활동지의 ‘추가 비용’에는 에이전트 수만 적지 않습니다. **불필요한 재실행, 중복 문맥, 취합, 사람의 최종 확인** 중 이 사례에서 가장 큰 비용 하나를 고르고 줄일 방법을 적습니다. 숫자 계산은 풀이에서 비교하며 개인 활동 시간을 추가하지 않습니다.

### 다음 실행을 허용할 근거를 남깁니다

|마지막 결과|다음 행동의 예|남길 기록|
|---|---|---|
|새 결함과 재현 입력이 확보됨|정해진 범위의 수정 한 번 배정|후보 버전, 실패 입력, 기대 결과|
|같은 결함에 같은 수정만 반복|자동 재배정을 멈추고 인계|이미 시도한 변경과 실패 근거|
|필수 검토 하나가 시간 안에 오지 않음|합격 취합을 보류하고 담당 실행 상태 확인|누락된 역할, 마지막 응답, 사용한 예산|
|원래 검사 통과, 필요한 검토 모두 확보|사람의 최종 확인으로 넘김|동일 후보에 대한 결과와 남은 한계|

시도 횟수·경과 시간·비용은 서로 다른 제한입니다. 횟수만 제한하면 한 실행이 오래 걸리는 문제를 막지 못합니다. 반대로 제한에 닿았다고 작업이 성공한 것은 아닙니다. 이 활동의 목적은 ‘끝날 때까지 반복’이라는 지시를 검증 가능한 실행·중단 조건으로 바꾸는 데 있습니다.

상태를 파일에 기록하는 것만으로 중복 배정이 사라지지는 않습니다. 두 실행이 동시에 같은 미완료 항목을 읽을 수 있기 때문입니다. 운영으로 옮길 때는 한 작업의 담당자를 어떻게 정하고, 담당 실행이 끊겼을 때 언제 다시 맡길지도 결정해야 합니다. 공통 활동에서는 그 규칙을 문장으로 쓰며 별도 스케줄러를 구현하지 않습니다.

## 하이프와 효과를 구분합니다

X의 Hamel Husain 게시물은 제목이 “Loop Engineering Is Dead. Enter Graph Engineering”이지만, 실제 본문은 “Stop it” GIF입니다. 새로운 방법을 상세히 제안하는 글이 아니라 유행어 교체를 풍자하는 맥락으로 읽어야 합니다. [실제 게시물](https://x.com/HamelHusain/article/2078346425621237935)

2026년 8월의 Loop Engineering 탐색 연구도 정의·구성 요소를 정리하면서 새로움과 효용에 관한 논쟁, 생산성 주장에 대한 체계적 증거 부족을 함께 기록합니다. 논문이 나왔다는 이유만으로 효과가 입증된 것은 아닙니다. [연구 원문](https://arxiv.org/abs/2608.21884)

짧고 한 사람이 쉽게 확인할 작업에는 한 에이전트와 직접 대화하는 편이 충분할 수 있습니다. 반복적인 작업 발견·검증이 필요할 때 Loop를, 독립된 여러 역할과 의존성 조정이 필요할 때 Graph를 검토합니다. 이 선택 기준을 설명하는 것이 공통 도달점입니다.

전체 그래프 런타임이나 장기 실행 자동화 구축은 수업 후 심화 범위입니다. 기존 [업무 수정 루프 구현](./build#loop)은 작은 제어 구조의 선택 연습으로 남깁니다.
